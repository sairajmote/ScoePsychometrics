1. OVERVIEW & CONNECTION
-------------------------
- Role: Primary persistent store for all project data (users, questions, responses, and reports).
- Engine: PostgreSQL (selected for relational integrity and JSONB support).
- Connection: Managed via SQLAlchemy in 'backend/database.py'.
- URL Source: DATABASE_URL variable in the root '.env' file.
- Status: Connected and fully functional.


2. SCHEMA RELATIONSHIPS (ERD LOGIC)
-----------------------------------
The database follows a strict hierarchical relationship to ensure data integrity:

[Users]
  |
  +--< [QuizSessions] (One user can have multiple sessions)
         |
         +--< [Responses] (One session has many individual answers)
         |
         +--< [Reports] (Each completed session generates one report)

- Foreign Keys:
  * QuizSessions.user_id -> Users.id
  * Responses.session_id  -> QuizSessions.id
  * Responses.question_id -> Questions.id
  * Reports.user_id      -> Users.id
  * Reports.session_id   -> QuizSessions.id


3. TABLE DETAILS & DATA CONSTRAINTS
------------------------------------

A. Users
   - Purpose: Identity and demographics.
   - Constraints: 'email' is UNIQUE and INDEXED to prevent duplicate candidate profiles.
   - Fields: id, name, email, education, created_at.

B. Questions
   - Purpose: Master question bank for MBTI, Temperament, and Enneagram.
   - Constraints: 'category' is INDEXED for fast filtering during test startup.
   - Fields: id, category, subtest, text, option_a to option_g, keyed, correct_answer.

C. QuizSessions
   - Purpose: Tracking individual test attempts.
   - Fields: id, user_id, status (in_progress/completed), started_at, completed_at, duration.

D. Responses
   - Purpose: The "Raw Data" layer. Stores every click made by a user.
   - Persistence: Individual responses are saved so that if a user disconnects, their
     progress is stored and can be analyzed at the item level later.

E. Reports
   - Purpose: The "Computed Data" layer.
   - Strategy: Uses PostgreSQL JSON format to store the finalized report.
   - Why JSON: Allows the backend to save a complex, nested dashboard structure
     (charts, text, scores) as one blob that the frontend can immediately render.
   - Constraints: 'report_id' (e.g., RPT-XXXX) is UNIQUE and INDEXED for fast lookup.

5. MAINTENANCE & CLI COMMANDS
------------------------------

To update the database schema (after editing models.py):
  alembic revision --autogenerate -m "description of change"
  alembic upgrade head

To seed/reset the question bank:
  python backend/seed_mbti.py
  python backend/seed_temperament.py
  python backend/seed_enneagram.py

To check database health:
  Visit: http://localhost:8000/health-db


6. DATA FLOW SUMMARY
---------------------
1. User starts -> Frontend fetches Category Questions from DB.
2. User answers -> Responses are saved to DB.
3. User submits -> Backend pulls Responses, runs scoring scripts.
4. Report generated -> Saved to Reports table as a JSON blob.
5. User views -> Frontend fetches JSON by Report ID and renders charts.
